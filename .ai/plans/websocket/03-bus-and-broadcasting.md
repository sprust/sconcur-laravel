# Шина рассылки и драйвер вещания Laravel

## Задача

`broadcast(new OrderShipped($order))` вызывается в http-воркере, в
rabbitmq-потребителе или в задаче пула. Соединения живут в ws-воркерах. Между ними
— граница процессов, и `Connection::write` её не пересекает: расширение
маршрутизирует запись по `id` внутри своего процесса.

## Почему fanout RabbitMQ

| Вариант | Почему нет |
|---|---|
| HTTP-API в ws-сервере, как у Reverb | ws-сервер не обслуживает маршрутов: не-Upgrade получает `426`; под `SO_REUSEPORT` у отдельного воркера нет адреса |
| Redis pub/sub | в `sconcur` нет асинхронного клиента Redis, а синхронный блокирует единственный PHP-поток вместе со всеми соединениями воркера |
| Опрос кеша | задержка и постоянная нагрузка вместо доставки |
| Свой socket-сервер-хаб отдельной группой | ещё одна группа, ещё одна точка отказа, и всё это ради того, что брокер уже умеет |

RabbitMQ в стеке уже есть, а `Channel::consume()` — генератор, который
приостанавливает корутину между доставками, то есть встраивается в цикл сервера
без единого блокирующего вызова.

Топология: обмен типа `fanout` (`sconcur.ws` по умолчанию), у каждого ws-воркера
своя очередь — имя выдаёт брокер (`declare` с пустым именем), флаги
`exclusive: true`, `autoDelete: false`, `durable: false`. Умер воркер — ушла
очередь вместе с его соединением к брокеру; накопления мусора нет по построению.

`autoDelete` здесь обязан быть выключен, и это не мелочь. Подписчик выходит из
генератора `consume()` на каждом простое, чтобы проверить реестр, — а выход из
генератора отменяет потребителя. С `autoDelete: true` брокер в этот момент сносит
очередь как оставшуюся без потребителей, и следующий `consume()` получает
`404 NOT_FOUND`, который заодно убивает канал: дальше только
`ChannelException: No channel available`. Первый прогон спайка сломался ровно так,
на второй секунде жизни. `exclusive: true` даёт ту же продолжительность жизни,
что и предполагалась, но привязывает её к соединению, а не к наличию потребителя.

Отсюда же второе правило: ошибка канала лечится переоткрытием канала, а не только
потребителя. Цикл восстановления подписчика — `catch` на простой (переоткрыть
потребителя), `catch` на всё остальное (переоткрыть канал, при неудаче —
соединение), с задержкой `reopen_backoff_ms` и записью в лог.

Обмен объявляет и потребитель (при подписке), и издатель (лениво, один раз на
процесс): это не очереди приложения, декларировать их отдельной командой
`sconcur:rabbitmq:declare` не нужно, потому что владелец здесь один — сам пакет.

## Интерфейс

```
src/Ws/Bus/BroadcastBusInterface.php  — publish(BroadcastMessageDto): void
                                        subscribe(Closure(BroadcastMessageDto): void): void
src/Ws/Bus/BroadcastMessageDto.php    — channels[], event, data, socket, timestamp
src/Ws/Bus/AmqpBroadcastBus.php       — fanout, боевой драйвер
src/Ws/Bus/LocalBroadcastBus.php      — доставка внутри процесса, только для тестов
src/Ws/Bus/BusSubscriber.php          — жизненный цикл корутины, переоткрытие
```

Тело сообщения — JSON: `{"channels":["private-orders.7"],"event":"OrderShipped",
"data":"{...}","socket":"12.34"}`. `data` — уже строка, ровно та, что уйдёт
клиенту: перепаковывать её в каждом воркере незачем.

`LocalBroadcastBus` честно называется тестовым: между процессами он ничего не
доставляет, и в README это должно быть сказано, а не подразумеваться.

## Драйвер вещания

`src/Ws/Broadcasting/SConcurBroadcaster.php` наследует
`Illuminate\Broadcasting\Broadcasters\Broadcaster` и реализует три метода:

- `auth(Request)` — снять префикс канала и прогнать колбэки `routes/channels.php`
  через `verifyUserCanAccessChannel`; публичный канал сюда не приходит;
- `validAuthenticationResponse(Request, $result)` — вернуть `['auth' => "key:hmac"]`,
  для presence добавить `channel_data`;
- `broadcast(array $channels, string $event, array $payload)` — собрать
  `BroadcastMessageDto` (вынув `socket` из полезной нагрузки) и опубликовать.

Регистрация в `SConcurServiceProvider` — тем же приёмом, что и очередь:
`$this->app->resolving(BroadcastManager::class, ...)` и `extend('sconcur', ...)`,
чтобы приложение, ничего не вещающее, не платило за построение менеджера.

Конфигурация приложения:

```php
// config/broadcasting.php
'sconcur' => [
    'driver' => 'sconcur',
],
```

Всё остальное — ключ, секрет, DSN шины — читается из `config('sconcur.ws')`, чтобы
не разносить одни и те же значения по двум файлам.

## `toOthers`

`broadcast(...)->toOthers()` кладёт в полезную нагрузку `socket` — тот самый
`socket_id`, что фронтенд прислал заголовком `X-Socket-ID`. Он едет в
`BroadcastMessageDto` и в каждом ws-воркере исключает ровно одно соединение при
раскладке по реестру. Заголовок в приложение попадает сам (`Echo` его ставит),
специальной middleware не требуется.

## Клиентские события

`client-*` разрешены только на `private-`/`presence-` и только при
`config('sconcur.ws.client_events')` — по умолчанию выключено, как и у Pusher.
Полученное клиентское событие воркер публикует в ту же шину с исключением
отправителя, то есть путь до других воркеров у него общий с обычным вещанием.
Дополнительно: ограничение частоты на соединение (простой счётчик в
`ConnectionState`) — иначе один клиент рассылает всем.

## Порядок и потери

Гарантий порядка между каналами нет и не планируется: fanout сохраняет порядок в
пределах одной очереди, чего достаточно. Сообщения не персистентны и не
подтверждаются с гарантией доставки (`autoAck: true` у подписчика): вещание —
это уведомление, а не задание; ws-воркер, который на секунду отвалился, должен
пропустить событие, а не получить его пачкой через минуту. Приложению, которому
нужна гарантия, нужна очередь, а не вещание, и это надо написать в README.
