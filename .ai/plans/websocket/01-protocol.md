# Протокол и авторизация каналов

## Почему протокол Pusher

Альтернатива — свой минимальный JSON-протокол и свой JS-клиент. Он проще на
неделю работы и дороже навсегда: приложению придётся отказаться от `laravel-echo`,
от `Echo.private()`, от `broadcastOn()`/`broadcastAs()` и писать переподключение,
буферизацию и подписки самому.

Совместимое подмножество Pusher v7 даёт всё это бесплатно:

```js
// resources/js/echo.js приложения — ничего своего
window.Echo = new Echo({
    broadcaster: 'pusher',
    key: import.meta.env.VITE_SCONCUR_WS_KEY,
    wsHost: import.meta.env.VITE_SCONCUR_WS_HOST,
    wsPort: 80,
    forceTLS: false,
    disableStats: true,
    enabledTransports: ['ws', 'wss'],
    cluster: '',
});
```

Реализуем подмножество, а не протокол целиком. Полный Pusher — это ещё
HTTP-API сервера, вебхуки, статистика, шифрованные каналы и cache-каналы; ничего
из этого Echo для обычного вещания не требует.

## Кадры

Все кадры — текстовые, JSON. Поле `data` в протоколе Pusher — строка с JSON
внутри (а не вложенный объект); это относится и к тому, что шлёт сервер, и к
тому, что шлёт клиент. Кодек обязан это соблюдать, иначе Echo молча не разберёт
кадр.

### Сервер → клиент

| Событие | Когда | `data` |
|---|---|---|
| `pusher:connection_established` | сразу после Upgrade | `{"socket_id":"...","activity_timeout":N}` |
| `pusher_internal:subscription_succeeded` | подписка принята | `{}`, для presence — блок `presence` |
| `pusher:pong` | ответ на `pusher:ping` | `{}` |
| `pusher:error` | отказ | `{"code":N,"message":"..."}` |
| `pusher_internal:member_added` / `member_removed` | presence, этап 3 | данные участника |
| прикладное событие | доставка из шины | полезная нагрузка вещания |

Прикладной кадр: `{"event":"OrderShipped","channel":"private-orders.7","data":"{...}"}`.

### Клиент → сервер

| Событие | `data` |
|---|---|
| `pusher:subscribe` | `{"channel":"...","auth":"key:hmac","channel_data":"..."}` |
| `pusher:unsubscribe` | `{"channel":"..."}` |
| `pusher:ping` | `{}` |
| `client-*` | произвольная нагрузка, только private/presence и только при включённой опции |

Всё, что не разобралось или не входит в список, — `pusher:error` и, если кадр
структурно битый, закрытие соединения.

## Каналы

| Префикс | Тип | Авторизация |
|---|---|---|
| нет | публичный | не требуется |
| `private-` | приватный | подпись обязательна |
| `presence-` | presence | подпись обязательна, плюс `channel_data` |
| `private-encrypted-` | шифрованный | не поддерживаем, отвечаем ошибкой |

Имя канала нормализуется один раз (`ChannelName` DTO: сырое имя, тип, имя без
префикса) — и Laravel, и протокол оперируют разными формами одного имени, и
смешивать их в строках нельзя.

## Подпись

Ws-воркер не ходит ни в базу, ни в сессию. Право на канал подтверждает подпись,
которую выдал http-воркер по обычному маршруту `/broadcasting/auth`:

```
signature = hash_hmac('sha256', "{socket_id}:{channel_name}", app_secret)
auth      = "{app_key}:{signature}"
```

Для presence в подписываемую строку добавляется третьим сегментом строка
`channel_data`: `"{socket_id}:{channel_name}:{channel_data}"`.

Проверка — `hash_equals`, никакого `==`. Ключ и секрет живут в
`config('sconcur.ws')` и приходят из ENV; секрет знают только http-воркеры (чтобы
подписать) и ws-воркеры (чтобы проверить), браузер видит только ключ.

Классы: `src/Ws/Auth/SignatureVerifier.php` (проверка, сторона ws) и
`src/Ws/Broadcasting/SConcurBroadcaster.php` (выдача, сторона Laravel — там же
`validAuthenticationResponse`).

## Коды ошибок

Диапазоны берём протокольные — от них зависит поведение Echo при
переподключении: `4000–4099` — не переподключаться, `4100–4199` — переподключиться
с задержкой, `4200–4299` — переподключиться сразу.

| Код | Когда |
|---|---|
| `4001` | ключ приложения в пути не совпал с `config('sconcur.ws.app_key')` |
| `4009` | подпись не сошлась, либо приватный канал без `auth` |
| `4100` | превышен лимит каналов на соединение или лимит соединений |
| `4200` | внутренняя ошибка обработчика, клиенту можно переподключиться |
| `4301` | не пришёл `pong` (клиент считается мёртвым) |

Точные коды и формулировки сверяются с поведением Echo на этапе 1 — это
внешний протокол, а не наш код, и подтверждается он живым клиентом.

## Путь подключения

Echo подключается на `/app/{app_key}?protocol=7&client=js&version=...`.
У `WsServer` параметр `path` — точное совпадение, а не префикс; чужой путь
получает `404` ещё до PHP.

Спайк снял вопрос, который тут был: query-строка в сравнение не входит, а
`Connection::path` отдаёт путь без неё. Значит, `path` группы — точная строка
`/app/{app_key}`, и клиент с чужим ключом получает `404` на рукопожатии, не
поднимая соединения вовсе. Проверено на четырёх URL: с query-строкой и без —
приняты, чужой ключ и корень — `404`.

Обработчик всё равно сверяет `$connection->path` и при несовпадении шлёт
`pusher:error` с кодом `4001`: `path` можно выставить в `''` (принимать любой
путь), и тогда проверка в PHP — единственная. Это одна строка кода, и она
страхует конфиг, а не дублирует его.

## Чего не делаем

- HTTP-API сервера (`/apps/{id}/events`) — заменён шиной.
- Вебхуки, статистика, `pusher:signin`, cache-каналы.
- Шифрованные каналы (`private-encrypted-`) — отвечаем ошибкой явно, а не молчим.
- `permessage-deflate` и TLS: сжатие расширение пока не умеет, TLS терминирует nginx.
