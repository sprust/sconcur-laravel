# Среда выполнения: группа, команда, обработчик соединения

## Группа мастера

Четвёртая группа в `config('sconcur.master.groups')`, по образцу `rabbitmq`:
её нет в конфиге, пока `SCONCUR_WS_WORKER_COUNT` меньше единицы. Тот же
`array_values(array_filter(...))` — он уже стоит вокруг списка групп и его нельзя
трогать.

```php
'name'         => 'ws',
'workerScript' => base_path('artisan'),
'workerCount'  => (int) env('SCONCUR_WS_WORKER_COUNT'),
'workerArgs'   => ['sconcur:servers:ws:start'],
'server'       => [...],
```

Блок `server` уходит в argv воркера дословно, поэтому команда обязана объявить
каждый флаг — Symfony Console отвергает неизвестные. Ровно та же история, что у
`HttpStartCommand` и `RabbitmqConsumerStartCommand`.

`WsServer::fromArgs` разбирает только скалярные параметры конструктора. Из
двадцати не проходят через argv три: `allowedOrigins`, `subprotocols` и `onError`.
Ни один из них нам не нужен — Echo не согласовывает субпротокол, а проверку
Origin делает наш же обработчик. Спайк прогнал весь предлагаемый набор флагов
через `fromArgs` целиком, включая `--path=` с пустым значением и `--masterPid`:
разбирается без ошибок. Значит, runner устроен как `HttpServerRunner` —
`WsServer::fromArgs($argv)` и ничего сверх того.

### Значения, которые нельзя выставить «как у http»

| Параметр | Значение | Почему |
|---|---|---|
| `handlerTimeoutMs` | `0` | обработчик живёт столько же, сколько соединение; любой дедлайн — это принудительный разрыв по таймеру |
| `idleTimeoutMs` | `0` | тишина в сторону сервера нормальна, живость держит ping |
| `pingIntervalMs` | `30000` | keepalive для push-only соединений |
| `maxConnections` | `0` | это не «сколько держать», а «после скольких обслуженных остановиться» |
| `path` | `''` | см. `01-protocol.md` |
| `reusePort` | `true` | пул на несколько процессов и rolling reload без отказов |

## Команда

`src/Console/WsStartCommand.php`, имя `sconcur:servers:ws:start`. Структура
копирует `HttpStartCommand`: список `RUNTIME_OPTIONS`, сигнатура с флагами,
`--masterPid`, и `configuredServerArgs()` — падение на блок `server` своей группы,
когда мастера нет (одиночный запуск в разработке). Группа ищется по
`workerArgs`, а не по имени, как и там.

Флаги: `address`, `reusePort`, `path`, `handshakeTimeoutMs`, `idleTimeoutMs`,
`writeTimeoutMs`, `pingIntervalMs`, `maxMessageBytes`, `maxConcurrency`,
`handlerTimeoutMs`, `maxConnections`, `shutdownTimeoutMs`, `preemptionQuantumMs`.

## Runner и обработчик

```
src/Ws/WsServerRunner.php     — собирает WsServer и запускает serve()
src/Ws/ConnectionHandler.php  — Closure(Connection): void, цикл одного соединения
src/Ws/ConnectionRegistry.php — реестр соединений и подписок процесса
src/Ws/ConnectionState.php    — socketId, Connection, каналы, данные участника
src/Ws/SocketIdGenerator.php  — socket_id в формате "<pid>.<счётчик>"
src/Ws/WsOptions.php          — DTO из config('sconcur.ws')
src/Ws/Protocol/              — кодек кадров, типы каналов, коды ошибок
src/Ws/Auth/SignatureVerifier.php
src/Ws/Bus/                   — шина, см. 03-bus-and-broadcasting.md
src/Ws/Broadcasting/          — драйвер вещания Laravel, см. там же
src/Ws/Events/                — события Laravel: открытие, закрытие, подписка
```

Цикл обработчика:

1. проверить путь и ключ приложения, иначе `pusher:error` + `close()`;
2. выдать `socket_id`, зарегистрировать соединение в реестре;
3. отправить `pusher:connection_established`;
4. `while (($message = $connection->read()) !== null)` — разобрать кадр и
   выполнить: `subscribe`, `unsubscribe`, `ping`, `client-*`;
5. в `finally` — снять соединение с учёта во всех каналах.

Пункт 5 обязан быть в `finally`: обработчик может быть размотан
`FlowStoppedException` при остановке сервера, и реестр не должен пережить
соединение. Утечка здесь — это запись в реестре, в которую воркер будет писать
до конца жизни процесса.

`socket_id` формата `\d+\.\d+` — этого требует протокол. Берём `pid` процесса и
монотонный счётчик: уникальность внутри процесса гарантирована счётчиком, между
процессами пула — pid.

## Корутина шины и graceful shutdown

Здесь единственное неочевидное место всей задачи. Спайк этапа 0 прошёл его
целиком — и подтвердил риск, и подтвердил решение (`08-spike.md`).

`Scheduler::serve` при остановке перестаёт принимать соединения и ждёт, пока
`spawnedCount` не станет нулём — то есть пока не завершатся все порождённые
корутины. Корутина-подписчик шины, живущая вечным циклом, этот счётчик никогда не
отпустит. В спайке это выглядело так: обработчик соединения вернулся, порождённая
им корутина продолжала тикать, `SIGTERM` пришёл через секунду — и процесс прожил
ещё семь, до конца тиков, а диагностика простоя назвала виновника поимённо
(`tracked=[sp_2=suspended]`). На боевом пуле это ожидание до `shutdownTimeoutMs`
и `SIGKILL` следом.

Решение — привязать жизнь подписчика к наличию соединений:

- реестр пуст, приходит первое соединение → обработчик поднимает подписчика
  через `Scheduler::get()->spawn(...)`;
- подписчик между доставками проверяет реестр и, найдя его пустым, выходит;
- при остановке расширение закрывает соединения, `read()` возвращает `null`,
  обработчики возвращаются, реестр пустеет — и подписчик уходит сам.

Чтобы «между доставками» наступало и на молчащей шине, соединение подписчика к
брокеру открывается со своим `readTimeoutSeconds`: истёкшее ожидание поднимает
`QueueException` («Consumer timeout exceed»), что для генератора
`Channel::consume` — именно простой, а не конец. Ловим, проверяем реестр,
переоткрываем потребителя. Так же — с задержкой и записью в лог — обрабатывается
настоящий обрыв: свой цикл переоткрытия, как у супервизорного потребителя
библиотеки.

Спайк прошёл этот путь целиком: соединение открылось, подписчик поднялся из
корутины обработчика, простой разбудил его через `readTimeoutSeconds`, событие,
опубликованное посторонним процессом, доехало до браузерной стороны, клиент
отключился — и подписчик ушёл на следующем пробуждении, после чего `SIGTERM`
завершил сервер за миллисекунду. Цена — задержка не больше `readTimeoutSeconds`
плюс двухсекундная пауза, которую расширение даёт push-only соединениям.

Запасные варианты (поднимать подписчика до `serve()` и оборачивать обработчик
`SIGTERM` библиотеки; просить в `sconcur` штатный хук фоновой корутины) больше не
нужны и в работу не берутся.

## Коротко о контексте корутины

`LaravelHttpHandler` кладёт запрос в `Context::current()`, и контейнер разрешает
`request`/`session`/`auth` по корутине. Ws-обработчику из этого не нужно ничего:
запроса нет, сессии нет, пользователь известен только по подписи. Поэтому
контекст соединения — это наши собственные ключи (socket_id), и никакие
`ScopedService` не трогаются.

События Laravel (`ConnectionOpened`, `ChannelSubscribed`, `ConnectionClosed`,
`ClientEventReceived`) диспатчатся через `AsyncDispatcher` — он уже
покорутинный. Слушатели пишет приложение; пакет их не имеет.

## Телеметрия и reload

Ws-сервер сам шлёт снапшоты в коллектор мастера (секция `connections`, как у
socket-сервера), никакого кода с нашей стороны. `sconcur:servers:master:reload`
делает rolling restart: соединения группы рвутся, Echo переподключается сам —
это надо сказать в README прямым текстом, потому что для http-пула reload
незаметен, а здесь заметен.
