# Пул периодических задач

Третья форма рантайма пакета — рядом с HTTP-сервером (`src/Http`) и пулом консьюмеров
очередей (`src/Queue/Rabbitmq`). Один процесс держит несколько периодических задач, по
корутине на каждую, с общим циклом, общими паузами и одной остановкой на всех.

Зачем: типовая фоновая задача в Laravel — это команда с вечным `while` внутри, своим
`sleep()` и своим самодельным способом остановиться. Каждая такая команда занимает
процесс со своим бутстрапом, а её `sleep()` замораживает этот процесс целиком. В пуле
`sleep` усыпляет только свою корутину, поэтому одна задача ждёт Mongo, пока другая
работает, а цикл и остановка написаны один раз.

## Задача

```php
use SConcur\Laravel\Tasks\TaskInterface;
use SConcur\Laravel\Tasks\TickResultEnum;

class CleanupTask implements TaskInterface
{
    public function name(): string
    {
        return 'cleanup';
    }

    public function tick(): TickResultEnum
    {
        $deleted = $this->action->handle();

        return $deleted > 0 ? TickResultEnum::Worked : TickResultEnum::Idle;
    }
}
```

Задача описывает одну порцию работы и больше ничего. Цикл, паузы, обработка исключений,
пересоздание и остановка — забота пула.

`stop()` в интерфейсе нет намеренно. PHP не умеет вмешаться в чужой фибер, поэтому такой
метод мог бы только поднять флаг, который цикл задачи обязан не забыть проверить. Раз
своего цикла у задачи нет, проверять нечего: пул просто перестаёт звать `tick()`.

Два правила, которые пул за вас не проверит:

1. **Тик обязан вернуться сам.** Прервать его нечем. Тик, который висит вечно, держит
   свою корутину до жёсткого дедлайна остановки, а тот разматывает всю группу.
2. **Тик не трогает глобальное состояние процесса** — `config()->set`, `Auth`, `Request`,
   статические свойства. Тики разных задач чередуются. Транзакция в этот список не
   входит, если соединение `sconcur_mysql`: её уровень вложенности хранится по корутинам,
   а расширение закрепляет её за отдельным физическим соединением, поэтому соседняя
   задача в неё не попадёт. На PDO-соединении — входит: там объект PDO один на процесс.

## Результат тика и паузы

`TickResultEnum` — единственное, что задача сообщает пулу, и от него зависит пауза:

| Результат | Когда возвращать | Пауза |
| --- | --- | --- |
| `Worked` | работа была | `busy`, обычно 0 — разобрать накопившуюся работу |
| `Idle` | работы не нашлось | `idle` |
| `Failed` | ставит пул сам, поймав исключение | `backoff` |

Исключение из тика пул сообщает через `ExceptionHandler`, пишет в лог и превращает в
`Failed`. Наружу оно не выходит: `WaitGroup::iterate()` бросает первое же исключение
любого участника и в `finally` останавливает группу, поэтому вышедшее наружу исключение
одной задачи погасило бы все остальные.

## Конфигурация

```php
'tasks' => [
    'control_key'              => 'sconcur:tasks:control',
    'lock_path'                => storage_path('sconcur/runtime/tasks.lock'),
    'memory_mb'                => 256,
    'sleep_chunk_ms'           => 250,
    'preemption_quantum_ms'    => 1000,
    'report_ticks'             => true,
    'shutdown_timeout_seconds' => 20,

    'list' => [
        ['name' => 'cleanup', 'task' => CleanupTask::class, 'idle' => 1, 'busy' => 0, 'backoff' => 3],
    ],
],
```

Задачи резолвятся из контейнера по имени класса, поэтому они — обычные сервисы с
внедрением зависимостей, а конфиг кэшируется как любой другой.

Полный перечень ENV — в [configuration.ru.md](configuration.ru.md).

## Команды

```sh
php artisan sconcur:tasks:start                          # весь пул в foreground
php artisan sconcur:tasks:start --only=cleanup           # только эти задачи
php artisan sconcur:tasks:stop                           # остановить пул
php artisan sconcur:tasks:stop --task=cleanup            # снять с тика одну задачу
php artisan sconcur:tasks:restart --task=cleanup         # пересоздать инстанс задачи
```

`stop` и `restart` кладут команду в кэш, а не шлют сигнал, — так пулом можно управлять
из другого контейнера, не зная его pid.

Команды копятся списком, а не перезаписывают друг друга: пул забирает их на своём тике, и
две команды, посланные внутри одного такого окна (`stop --task=cron`, следом
`stop --task=indexes`), иначе оставили бы только вторую. И добавление, и выборка идут под
локом кэша, потому что каждая — это чтение и запись с сетевым обходом между ними: два
artisan-процесса, запущенных разом, оба прочитали бы пустой ключ и оба записали список из
одного элемента. Если лок не дался за три секунды, работа делается без него: читатель,
который сдался, сделал бы пул глухим к командам, а писатель — потерял бы команду
остановки в деплой-скрипте.

Забирая команды, пул берёт только те, что новее его собственного старта, и чистит ключ:
иначе оставшийся в кэше `stop` останавливал бы и тот процесс, который супервизор поднимет
взамен, и так до бесконечности.

Остановка одной задачи живёт столько же, сколько процесс. Выключить задачу насовсем —
это конфиг, а не команда.

`restart` означает ровно одно: выбросить инстанс задачи и построить новый. Задача копит
состояние между тиками (последняя обработанная минута, таймер следующей чистки), и
сбросить его — это всё, что тут можно перезапустить.

## Одна копия задачи

На старте пул берёт `flock` на каждую задачу отдельно — `lock_path` плюс её имя, — и не
поднимается, если хоть один не достался. Лок именно на задачу, а не на процесс: дважды не
должен идти крон, а не пул как таковой. Поэтому две точки входа с `--only=` спокойно
работают рядом, `cron:start` в одном терминале и монитор в другом, а второй крон не
стартует ни в пуле, ни отдельной командой.

`flock`, а не лок в кэше, по той же причине, по которой его использует мастер библиотеки:
ядро отпускает блокировку при смерти процесса, включая `SIGKILL`, поэтому протухшего
лока не бывает и TTL обновлять не надо.

## Остановка

Любая причина ведёт по одному пути: контролёр снимает задачи с тика, ждёт, пока текущие
тики закончатся, и выходит. Причины — `SIGTERM`/`SIGINT`/`SIGQUIT`, команда
`sconcur:tasks:stop`, превышение `memory_mb`.

Различает их код выхода, и это не мелочь. Остановка по просьбе выходит с нулём, выход по
`memory_mb` — с `TaskPool::EXIT_RESTART` (75). Группа `tasks` объявляет
`restartPolicy: on-failure`, поэтому мастер поднимает новый процесс после второго и
оставляет в покое после первого. С унаследованным от мастера `always` любой выход
означал бы новый пул через секунду, и `sconcur:tasks:stop` останавливал бы пул ровно до
следующего тика — то есть не останавливал бы вовсе.

Контролёр — такой же участник группы, только без полезной работы: он просыпается раз в
`sleep_chunk_ms` и смотрит сигнал и канал управления. Это не украшение. Обработчик
`pcntl` выполняется на границе опкодов, то есть только когда исполняется PHP-код, а
процесс, все корутины которого припаркованы в ожидании Go, не исполняет ничего — и
`SIGTERM` лежит недоставленным. Поэтому паузы дробятся на кванты: серверы самой
библиотеки поллят с тем же интервалом и по той же причине.

Если за `shutdown_timeout_seconds` кто-то не вышел, контролёр называет застрявшие задачи
в логе и разматывает группу через `WaitGroup::stop()`. Разматывается вся группа сразу —
отдельную корутину принудительно снять нечем: `WaitGroup` держит их fiber id в
защищённом свойстве, а `Scheduler::detach()` убирает корутину с планирования, не
разматывая её, так что `finally` не отработают. Поэтому дедлайн выборочной остановки
одной задачи не разматывает ничего: он только пишет предупреждение, ведь остальные
задачи продолжают работать.

Дедлайн обязан быть меньше того, что даёт на остановку тот, кто пул супервизит, иначе
процесс всегда добивается `SIGKILL` и мягкий путь не выполняется никогда. Под мастером
цепочка растёт наружу и её надо держать в этом порядке:

```
shutdown_timeout_seconds пула (20 с)
  < shutdownTimeoutMs группы tasks (30 000 мс)
    < stopwaitsecs программы мастера в supervisor (40 с)
```

## Под мастером

Пул рассчитан на роль группы мастера, и это его штатный режим:

```php
[
    'name'          => 'tasks',
    'workerScript'  => base_path('artisan'),
    'workerCount'   => 1,
    'workerArgs'    => ['sconcur:tasks:start'],
    'restartPolicy' => 'on-failure',
    'shutdownTimeoutMs' => 30000,
],
```

`workerCount` — ровно 1, и это не формальность: `0` для мастера означает не «ни одного»,
а «по воркеру на ядро», а два пула рядом означали бы два крона, тикающих одну и ту же
минуту. От второго пула защищает и `flock`, но конфиг не должен на это полагаться.

Мастер дописывает `--masterPid` в argv любого своего воркера, поэтому команда объявляет
этот флаг — иначе Symfony Console отвергнет неизвестный аргумент. Пул использует его так
же, как серверы библиотеки: контролёр на своём тике сверяет `posix_getppid()` с этим pid
и, если мастер умер и ядро переприсвоило родителя, штатно останавливается. Сравнение
идёт по родителю, а не по «жив ли такой pid», потому что pid может быть переиспользован.

**Телеметрия у пула своя, на PHP.** Панель наполняют снапшоты, которые раз в секунду
шлют серверный и консьюмерский рантаймы расширения; пул не запускает ни того, ни другого,
поэтому `TaskPoolTelemetry` сэмплит и отправляет их сам. Канал — открытый контракт:
unix-сокет из `SCONCUR_TELEMETRY_SOCKET`, 4-байтовый big-endian префикс длины, тело
`{"t":"snapshot","s":<snapshot>}`; имя воркера мастер кладёт в `SCONCUR_SERVER_NAME` как
`<группа>:<индекс>`, и группа выводится из него по последнему двоеточию.

Что PHP замерить может: RSS из `/proc/self/status` и CPU по дельте `/proc/self/stat` —
те же источники, что читает расширение. Чего не может: память рантайма расширения и число
его живых задач у этого воркера просто не существуют и уходят нулями.

Из трёх секций нагрузки `requests` и `connections` не шлются — они принадлежат серверу и
сокет-серверу, — а секцию, которую никто не прислал, коллектор в ответ не кладёт вовсе.
Третью, `consumers`, пул шлёт: тик для задачи — то же, что доставка для консьюмера, и
счётчики ложатся на неё один в один, поэтому колонки панели «In process / Finished /
Refused» наполняются без изменений на её стороне.

| Поле секции | Что значит у пула |
| --- | --- |
| `coroutines` | сколько задач в пуле — по корутине на каждую, то есть ёмкость |
| `delivered` | тиков, в которых была работа |
| `acked` | из них завершились нормально — вместе с `refused` дают колонку Finished |
| `refused` | из них упали с исключением — колонка Refused, и часть Finished |
| `timed` / `avgMs` | сколько тиков замерено и их средняя длительность |
| `inFlight` + корзины возраста | тики, идущие прямо сейчас, и как давно |

Холостой тик (`TickResultEnum::Idle`) не считается нигде. Задача, опрашивающая раз в
секунду работу, которой нет, — это пустое ожидание консьюмера, а не доставка: считай мы
их, Finished мерил бы интервал опроса, а `avgMs` — стоимость пустого опроса вместо
стоимости работы.

Мастер суммирует эту секцию по всем воркерам, поэтому его сводные «доставок в секунду» и
средняя длительность считают тики пула вместе с настоящими доставками AMQP-пула.
Пер-групповые числа при этом остаются чистыми. Выключается `report_ticks`.

Отправка best-effort и at-most-once: сокет неблокирующий, коллектор, переставший читать,
не тормозит пул ни на сколько, а потерянный кадр стоит секунды свежести и не повторяется.
Недописанный кадр — другое дело: поток length-prefix, и половина кадра заставит коллектор
прочитать заголовок следующего как хвост этого тела и разъехаться на всём дальнейшем.
Поэтому короткая запись закрывает соединение, следующая отправка переподключается, и
теряется только этот снапшот. Закрытие соединения означает для мастера, что воркер ушёл.
Мастер помечает воркера `hung`, если снапшота не было дольше 15 секунд.

Группу, про которую панель молчит — например при остановленном пуле, — дашборд приложения
дорисовывает нулями, чтобы она не выглядела несуществующей (`SconcurStatClient`).

## Преемпция

`preemption_quantum_ms` включает автоматическое переключение корутин: расширение по
таймеру прерывает VM и паркует текущую корутину, поэтому тик, ушедший в чистые
вычисления, не может заморозить соседей. Включено, квант 1000 мс.

Заморозить надо не дать в первую очередь контролёру: именно его тик доставляет сигнал
(обработчик `pcntl` выполняется только когда исполняется PHP-код) и опрашивает канал
управления. Без преемпции долгий невытесняемый участок внутри чужого `tick()` откладывает
и то и другое, то есть бьёт по остановке пула.

Квант грубее дефолтных 5 мс библиотеки намеренно. Те 5 мс рассчитаны на сервер, где
десятки обработчиков делят поток и латентность соседнего запроса считается в
миллисекундах; здесь несколько корутин, большая часть времени — сон, и ответа никто не
ждёт. Худший случай реакции на `SIGTERM` — квант преемпции плюс квант сна, около 1.25 с
против 20-секундного дедлайна остановки.

Нативный блокирующий вызов преемпция не вытесняет — только userland-код PHP. Для него
есть жёсткий дедлайн остановки.

`0` выключает. Это нужно задаче, которая держит транзакцию MySQL на общем соединении
`mysql`: там PDO-объект один на процесс, и преемпция позволяет соседней задаче попасть
внутрь чужой транзакции. На `sconcur_mysql` такого нет — см.
[database.ru.md](database.ru.md).
