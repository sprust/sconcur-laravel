# Redis (клиент `sconcur` и кэш-стор `sconcur_redis`)

Фича Redis из SConcur, подключённая к Laravel в двух местах:

- клиент `sconcur` для `RedisManager` — `Redis::`, `Redis::connection()`,
  `Redis::throttle()`, `Redis::funnel()`, а с ними и драйвер очереди `redis` из Laravel;
- кэш-стор `sconcur_redis` — `Cache::`, локи и теги.

Команда уходит в расширение, а вызывающая корутина на это время приостанавливается.
Команды, которые много корутин отправляют одновременно, идут по мультиплексированным
соединениям расширения одним пайплайном и возвращаются за один обмен с сервером. Вне
корутины те же вызовы работают синхронно. Что умеет и чего не умеет сама фича — в
документации библиотеки, `vendor/sconcur/sconcur/docs/redis.ru.md`.

## Соединения

Соединения описываются там же, где их держит Laravel, — в секции `redis` файла
`config/database.php`, отдельными полями:

```php
// config/database.php
'redis' => [
    'client' => env('REDIS_CLIENT', 'sconcur'),

    'options' => [
        'prefix' => env('REDIS_PREFIX', Str::slug((string) env('APP_NAME', 'laravel'), '_') . '_database_'),
    ],

    'default' => [
        'url'        => env('REDIS_URL'),
        'host'       => env('REDIS_HOST', '127.0.0.1'),
        'port'       => env('REDIS_PORT', '6379'),
        'username'   => env('REDIS_USERNAME'),
        'password'   => env('REDIS_PASSWORD'),
        'database'   => env('REDIS_DB', '0'),
        'timeout_ms' => 5000,
    ],

    'cache' => [
        'url'        => env('REDIS_URL'),
        'host'       => env('REDIS_HOST', '127.0.0.1'),
        'port'       => env('REDIS_PORT', '6379'),
        'username'   => env('REDIS_USERNAME'),
        'password'   => env('REDIS_PASSWORD'),
        'database'   => env('REDIS_CACHE_DB', '1'),
        'timeout_ms' => 5000,
    ],
],
```

Секцию нужно выписать целиком. Из `config/database.php` Laravel сливает со своим файлом
только `connections`, поэтому секция `redis` приложения заменяет секцию фреймворка, а не
дополняет её. Здесь это и нужно: в записях фреймворка есть `max_retries` и `backoff_*`, и
клиент от них отказывается.

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `scheme` | `tcp` | `tcp`, `tls` или `unix` |
| `host` | `127.0.0.1` | хост сервера; IPv6-адрес принимается как есть |
| `port` | `6379` | порт сервера |
| `path` | — | сокет, для `scheme => unix` |
| `username` | — | пользователь ACL |
| `password` | — | пароль |
| `database` | `0` | номер базы |
| `url` | — | URL `redis://`, `rediss://` или `tls://`; сливается с полями так же, как это делает `RedisManager`, и перекрывает их |
| `timeout_ms` | `30000` (расширения) | дедлайн одной команды; `0` — без дедлайна |
| `pool_size` | `4` (расширения) | мультиплексированных соединений на процесс для этого сервера; не больше 64 |
| `conn_max_lifetime_ms` | без ограничения | сколько соединение живёт в пуле, прежде чем его заменят |
| `prefix` | `redis.options.prefix` | ставится перед ключами, как у phpredis; см. [префикс ключей](#префикс-ключей) |

`SConcur\Laravel\Redis\Dsn` собирает из полей DSN фичи: `redis://` для `tcp`, `rediss://`
для `tls`, `unix://путь?db=&user=&pass=` для сокета. Имя пользователя и пароль кодируются
процентами, так что в них допустим любой символ.

При создании соединения ничего не открывается. Пул фичи поднимается в расширении первой
командой, а неиспользуемый пул закрывается там через пять минут после последней.

## От чего клиент отказывается

Настройка, которую фича не читает, отвергается при создании соединения, а не
игнорируется: если настройку никто не читает, соединение ведёт себя не так, как написано в
конфиге. Все исключения ниже наследуют `LogicException`, а в сообщении названа замена,
если она есть.

| Исключение | Когда |
|---|---|
| `RedisClusterNotSupportedException` | запрошена запись из `redis.clusters` |
| `UnsupportedRedisOptionException` | в записи соединения есть ключ не из таблицы выше, и он чем-то задан; в `redis.options` есть ключ, который клиент не читает, и он чем-то задан — клиент читает `prefix` и `cluster`, а `parameters` принимает только пустым; значение, которое фича прочитала бы не так, как оно записано, — см. ниже |
| `UnsupportedRedisCallException` | вызов из списка в разделе [«Фасад»](#фасад) |

Все три лежат в `SConcur\Laravel\Redis\Exceptions\`.

«Чем-то задан» — значит, значение не `null`, `false`, `''`, `0`, `'0'` и не `[]`: в
скелете Laravel есть `persistent => false` и `username => null`, а выключенная настройка
ничего не просит. `redis.options.cluster` принимается с любым значением: он лишь говорит,
как шардируются записи `redis.clusters`, а запрос любой из них отвергается сам по себе.

Отвергается и значение, которое фича приняла бы без возражений, но использовала бы не так,
как оно записано:

| Значение | Почему |
|---|---|
| `database`, `port`, `timeout_ms`, `conn_max_lifetime_ms` — не целое число или отрицательное | `'abc'` превратилось бы в `0`, а `0` у большинства из них значит своё; число строкой, как его отдаёт `env()`, принимается |
| `port` вне 1…65535 | такого порта нет |
| `pool_size` вне 1…64 | расширение урезает больший пул до 64, а 0 читает как своё значение по умолчанию |
| `scheme` — не `tcp`, `tls` или `unix` | такого транспорта нет |
| `host` содержит `://` | схема задаётся в `scheme` |
| `host` начинается с `/` | сокет — это `scheme => unix` и `path` |
| `path` при `tcp` или `tls`; `host` или `port` при `unix`; `unix` без `path` | при этой схеме ключ не читается |
| `username` без `password` | драйвер логинится только при наличии пароля, и соединение работало бы от пользователя по умолчанию |
| `prefix` — не строка | он ставится перед ключом как есть |

Ключи, которые приложения переносят чаще всего, и почему каждый отвергается:

| Ключ | Вместо него |
|---|---|
| `max_retries`, `backoff_*` | упавшее соединение расширение восстанавливает само, а команду не повторяет никогда: сервер мог её выполнить и потерять только ответ |
| `timeout`, `read_timeout` | `timeout_ms` |
| `persistent` | соединения и так переживают запрос — они живут в пуле расширения |
| `name` | ничего: `CLIENT SETNAME` переименовал бы соединение, которым пользуются другие корутины |
| `serializer`, `compression` | на клиенте ничего; кэш-стор сериализует сам |
| `protocol` | ничего: RESP3 меняет форму ответа нескольких команд, а поддерживается только RESP2 |

## Фасад

`'client' => 'sconcur'` переводит `Redis::` на `SConcur\Laravel\Redis\Connection`, и отвечает он
так же, как `PhpRedisConnection` из Laravel. `Redis::` — тонкая прослойка, а не отдельная
абстракция: кроме методов, которые Laravel переопределяет, вызов уходит прямо в клиент, так
что код, написанный под фасад, написан под phpredis — клиент Laravel по умолчанию и самый
распространённый. `tests/Feature/Redis/PhpRedisParityTest.php` выполняет одни и те же вызовы
через `PhpRedisConnection` и через это соединение на одном сервере и требует одинаковых
ответов.

```php
Redis::set('greeting', 'hello', 'EX', 60, 'NX');   // true, или false, если ключ уже есть
Redis::get('missing');                             // null
Redis::hget('hash', 'missing');                    // false
Redis::hgetall('hash');                            // ['field' => 'value']
Redis::zrange('ranking', 0, -1, true);             // ['member' => 1.0]
Redis::expire('greeting', 10);                     // true
Redis::type('greeting');                           // 1, Redis::REDIS_STRING
```

- Методы, которые переопределяет `PhpRedisConnection`, переопределены с теми же сигнатурами и
  результатами: `get`, `mget`, `set`, `setnx`, `hmget`, `hmset`, `hsetnx`, `lrem`, `blpop`,
  `brpop`, `spop`, `zadd`, `zrangebyscore`, `zrevrangebyscore`, `zinterstore`,
  `zunionstore`, `eval`, `evalsha`, `flushdb`, `executeRaw`, `pipeline`, `transaction`,
  `subscribe`, `psubscribe`.
- Любой другой вызов читается с сигнатурой phpredis, как и каждый вызов через
  `Redis::command()` и на пакете пайплайна или транзакции. Там, где сигнатура принимает массив
  опций или свой порядок аргументов, её разбирает `SConcur\Laravel\Redis\PhpRedisArguments`:
  `zRange`/`zRevRange` с `true` или `['withscores', 'byscore', 'bylex', 'rev', 'limit']`,
  `zRangeByScore`/`zRevRangeByScore` с `['withscores', 'limit']`, `zAdd` с флагами перед
  парами, `zInterStore`/`zUnionStore`, `set` с TTL или `['nx', 'ex' => 10]`,
  `lRem(key, value, count)`, `eval`/`evalSha(script, arguments, numberOfKeys)`, `sort`,
  `xAdd`, `xRead`, `lPos`, `getEx`, `copy`, `flushDb`/`flushAll` с `async`, `rawCommand`.
  Остальные методы принимают аргументы команды по порядку.
- На самом фасаде побеждают переопределения, как и у `PhpRedisConnection`: `Redis::set()`,
  `Redis::lrem()` и `Redis::eval()` принимают порядок Laravel, а порядок phpredis для тех же
  команд работает через `Redis::command()` и внутри пакета.
- Ответ приводится к форме phpredis в `SConcur\Laravel\Redis\PhpRedisReplies`: статус команды,
  которая только подтверждает, — `true`; nil — `false` (переопределения Laravel возвращают
  `null` для `get`, `mget`, `blpop` и `brpop`); команды «да/нет» вроде `expire`,
  `sismember` и `hexists` — `bool`; счёты и дробные счётчики — `float`; `type` —
  целочисленная константа phpredis; `hgetall`, `config get`, `zpopmin`/`zpopmax` и всё с
  `WITHSCORES` — карты; `hmget` внутри пакета — карта по полям; `info` разбирается в карту;
  `xrange`/`xrevrange` отвечают картой id => поля, `xread`/`xreadgroup` — стрим => id => поля,
  а чтение, которое ничего не нашло, — `[]`.
- Один уровень массива в аргументах раскрывается на месте, и как именно — решает команда:
  PHP хранит `['0' => 'a', '1' => 'b']` ровно так же, как `['a', 'b']`, поэтому по форме
  карту от списка не отличить. `mset`, `msetnx`, `hset` и `hmset` раскрывают любой массив
  парами «ключ, значение»; `zadd` принимает замыкающую карту `member => score`; сигнатуры
  phpredis выше читают свои массивы опций; все остальные команды раскрывают список
  поэлементно, а ассоциативный массив отвергают с `InvalidRedisArgumentException`. Всё, что
  глубже, а также `bool` и `null` в любом месте, отвергается тем же исключением.
- Блокирующая команда получает дедлайн, который нужен её ожиданию: само ожидание плюс
  `timeout_ms`, а при бесконечном ожидании — без дедлайна. Ожидание читается из аргументов
  так же, как его читает расширение, — `BLPOP`, `BRPOP`, `BZPOPMIN`, `BZPOPMAX`, `BLMOVE`,
  `BRPOPLPUSH`, `BLMPOP`, `BZMPOP`, `WAIT`, `WAITAOF`, а также `XREAD`/`XREADGROUP` с
  `BLOCK`. Плоский `timeout_ms` расширение отвергло бы как более короткий, чем ожидание.
- `Redis::funnel()` и `Redis::throttle()` возвращают лимитеры фреймворка с одним отличием:
  внутри корутины пауза между попытками приостанавливает вызывающего, а не замораживает
  воркер, — так же, как у [локов](#локи).
- `CommandExecuted` и `CommandFailed` отправляются так же, как у соединений фреймворка, —
  после `Redis::enableEvents()`.
- Собственный типизированный API фичи — `Redis::connection()->client()`, объект
  `SConcur\Features\Redis\Connection`: `scan()` как итератор, `blPop()` с рассчитанным
  дедлайном и остальное из `vendor/sconcur/sconcur/docs/redis.ru.md`.

Где поведение осознанно отличается от phpredis:

| phpredis | Здесь | Почему |
|---|---|---|
| отвергнутая команда отвечает `false`, а причину держит в `getLastError()` | `RedisCommandException` | `false` от `incr` или `hget` читался бы как ответ, а `WRONGTYPE` — как отсутствующий ключ |
| `scan($cursor)` двигает курсор через ссылку | `scan()`, `hscan()`, `sscan()` и `zscan()` отвечают `[курсор, элементы]`, у `hscan`/`zscan` элементы — карта | вызов фасада не может передать ссылку |
| статус, который вернул Lua-скрипт, — `true` | строка `'OK'` | фича отдаёт статус и строку одинаково |

Один объект соединения обслуживает все корутины процесса: сокета и своего состояния у него
нет.

Эти вызовы отвергаются с `UnsupportedRedisCallException` — и магическим вызовом, и через
`Redis::command()`:

| Вызов | Вместо него |
|---|---|
| `multi`, `exec`, `discard` | `Redis::transaction(function ($transaction) { ... })` |
| `watch`, `unwatch` | ничего: оптимистичной блокировке нужно соединение, закреплённое на несколько обменов |
| `select` | ключ `database` записи соединения |
| `auth` | ключи `username` и `password` |
| `hello` | ничего: поддерживается только RESP2 |
| `subscribe`, `psubscribe` командой | `Redis::subscribe($channels, $callback)` |
| `unsubscribe`, `punsubscribe` | ничего: подписка заканчивается, когда колбэк бросает исключение или завершается её корутина |
| `ssubscribe`, `sunsubscribe` | ничего: шардированный pub/sub существует для кластера |

Кроме этого фича сама отвергает `QUIT`, `CLIENT REPLY`, `MONITOR`, `SWAPDB` и остальное из
списка в её документации — со своим `UnsupportedRedisCommandException`.

## Префикс ключей

`prefix` задаётся в `redis.options` или в записи соединения — тогда он перекрывает опции, так
же, как его читает `PhpRedisConnector` из Laravel. Соединение ставит его туда же, куда
phpredis ставит `Redis::OPT_PREFIX`, так что ключ, записанный phpredis, находится здесь под
тем же именем. `tests/Feature/Redis/PhpRedisParityTest.php` прогоняет каждый вызов с
префиксом на обоих клиентах и требует одинаковых ответов и одинаковых ключей в базе.

```php
// redis.options.prefix = 'laravel_database_'
Redis::set('user:1', 'Ann');                          // SET laravel_database_user:1 Ann
Redis::eval($script, 1, 'user:1', 'arg');             // KEYS[1] с префиксом, ARGV[1] без
Redis::executeRaw(['GET', 'user:1']);                 // GET user:1 — без префикса
Redis::keys('user:*');                                // ['laravel_database_user:1']
Redis::_prefix('user:*');                             // 'laravel_database_user:*'
```

Префикс получают:

- все ключи команды, где бы команда их ни держала: `set`, `mget`, `mset`, `rename`, `blpop`
  (не таймаут), `eval`/`evalsha` (ключи, не аргументы), `zinterstore`, `xread` (стримы, не
  id), `bitop` и остальная таблица в `SConcur\Laravel\Redis\KeyPrefix`;
- каналы `publish` и `subscribe`, шаблоны `psubscribe`, шаблон `keys`;
- те же вызовы внутри `pipeline()` и `transaction()`.

Не получают — тоже как у phpredis:

- `executeRaw()` и `rawCommand()`;
- команда, которой нет в таблице, например команда модуля;
- шаблон `MATCH` у `scan()`, `hscan()`, `sscan()` и `zscan()`: пишите его с префиксом,
  `Redis::scan($cursor, ['match' => Redis::_prefix('user:*')])`;
- `BY`, `GET` и `STORE` у `sort`;
- имя ключа, которое Lua-скрипт собирает из своих аргументов;
- `Redis::connection()->client()`, собственный объект фичи.

Ответы содержат имена так, как их хранит сервер, с префиксом: `keys()` и `scan()` отдают их
с ним, и колбэк подписки получает канал с ним.

## Пайплайны и транзакции

```php
$replies = Redis::pipeline(function ($pipe): void {
    $pipe->set('a', 1);
    $pipe->incr('a');
    $pipe->get('missing');
});
// [true, 2, false]

$replies = Redis::transaction(function ($transaction): void {
    $transaction->incrby('counter', 2);
    $transaction->lpush('events', 'inc');
});
```

Колбэк получает `SConcur\Laravel\Redis\CommandBatch`. Он принимает те же вызовы, что и объект,
который phpredis отдаёт колбэку, с сигнатурами phpredis, и ничего не отправляет, пока колбэк
не вернётся. Затем пакет уходит за один обмен, а вызов отвечает списком ответов по порядку в
форме phpredis. `transaction()` оборачивает пакет в `MULTI`/`EXEC`, и сервер выполняет его
как одно целое.

- Команда, упавшая при выполнении, занимает своё место среди ответов как `false`, как в
  phpredis, а остальные всё равно выполняются — и в пайплайне, и в транзакции.
- Команда, которую сервер отверг при постановке транзакции в очередь (неверное число
  аргументов, неизвестная команда), — другой случай: `EXEC` отвечает `EXECABORT`, ни одна
  команда не выполняется, а вызов бросает `RedisCommandException` там, где phpredis
  отвечает `false`.
- Пакет без команд отвечает `[]` без обращения к серверу.
- Без колбэка возвращается сам пакет, и отправляет его `exec()`.
- `exec()` внутри колбэка бросает `NestedPipelineExecutionException`: он отправил бы уже
  собранные команды отдельно, вне транзакции.
- Колбэк не может ничего прочитать по ходу — все ответы приходят в конце.

## Pub/Sub

```php
Redis::subscribe(['news'], function (string $payload, string $channel): void {
    // ...
});

Redis::psubscribe(['user:*'], function (string $payload, string $channel): void {
    // ...
});
```

Колбэк получает содержимое сообщения и канал — так его вызывают соединения фреймворка. С
[префиксом ключей](#префикс-ключей) подписка идёт на каналы и шаблоны с префиксом, и колбэк
получает канал с префиксом, как у phpredis. Подписка владеет отдельным соединением, потому
что протокол переводит в режим подписчика само соединение. Цикл заканчивается, когда колбэк бросает исключение, когда
завершается корутина, в которой он идёт, или с `RedisConnectionException`, когда соединение
потеряно; соединение освобождается в любом случае. Ошибка при его закрытии не подменяет
исключение, которым закончился цикл.

`Redis::publish()` — обычная команда, она отвечает, сколько подписчиков получили
сообщение.

## Кэш-стор

```php
// config/cache.php
'stores' => [
    'sconcur_redis' => [
        'driver'          => 'sconcur_redis',
        'connection'      => env('REDIS_CACHE_CONNECTION', 'cache'),
        'lock_connection' => env('REDIS_CACHE_LOCK_CONNECTION', 'default'),
    ],
],
```

```dotenv
CACHE_STORE=sconcur_redis
```

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `connection` | `default` | соединение из `database.redis`, где лежат значения |
| `lock_connection` | `connection` | соединение, где лежат локи |
| `prefix` | `cache.prefix` | префикс стора, после префикса соединения, перед каждым ключом и именем лока |
| `events` | `true` | события кэша, как у любого стора |

Стор строит соединения из `database.redis` сам, тем же `SConcur\Laravel\Redis\Connector`,
что и фасад, а не через `RedisManager`. Поэтому он работает на фиче, что бы ни стояло в
`database.redis.client`, и отвергает те же записи соединений, что и клиент. `redis.options`
принадлежат клиенту фасада: стор проверяет их, только когда этот клиент — `sconcur`, а иначе
оставляет их phpredis или predis.

`prefix` соединения читается при любом клиенте фасада. Ключ — это префикс соединения, затем
префикс стора, затем сам ключ: то же имя, которое пишет `RedisStore` фреймворка на phpredis с
той же конфигурацией. С локом так же, на префиксе соединения локов. Поэтому два стора делят
значения и локи — это проверяет `SconcurRedisStoreTest` против `RedisStore` на phpredis.
Исключение — значения с тегами, см. ниже.

Штатный `RedisStore` фреймворка здесь не используется: он открывает транзакцию через
`multi()` и закрывает через `exec()` двумя отдельными вызовами, а на соединении, общем для
всех корутин, внутрь неё попали бы команды соседа. Поэтому
`SConcur\Laravel\Cache\Redis\Store` написан на типизированном API фичи.

| Метод | Команда |
|---|---|
| `get` | `GET` |
| `many` | `MGET` |
| `put` | `SET key value EX seconds`, не меньше 1 секунды |
| `putMany` | один `MULTI`/`EXEC` из `SET … EX` |
| `add` | `SET key value EX seconds NX` — атомарно, без скрипта |
| `increment`, `decrement` | `INCRBY`, `DECRBY` |
| `forever` | `SET` без срока жизни |
| `forget` | `DEL` |
| `flush` | `FLUSHDB` |

- Формат хранения — тот же, что у `RedisStore` фреймворка, так что они читают ключи друг
  друга. Конечное число пишется как есть — только поэтому на нём работает `INCRBY`, — а
  читается строкой с числом, которую держит Redis. Всё остальное проходит через
  `serialize()` и читается с `cache.serializable_classes` в качестве разрешённых классов.
- `flush()` очищает всю базу, на которую указывает соединение, включая чужие ключи, — как
  и `RedisStore`. Отведите кэшу отдельную базу.
- Теги работают через `TaggableStore` фреймворка, который хранит их в самом сторе. Это не
  схема `RedisStore`, чей `RedisTaggedCache` держит по отсортированному множеству на тег,
  поэтому значение, записанное с тегами одним стором, другой с тегами не найдёт, а тег,
  сброшенный через один стор, для другого не сбрасывается.

## Локи

`Cache::lock()` на этом сторе берёт лок через `SET NX` (с `EX`, если у лока есть срок), а
снимает и продлевает его Lua-скриптами самого фреймворка, так что сделать это может только
владелец. `restoreLock()`, `forceRelease()`, `refresh()` и `isOwnedByCurrentProcess()`
работают так же, как на Redis-сторе фреймворка.

`block()` отличается в одном месте — паузой между попытками. Фреймворк ждёт через
`usleep()`, а внутри корутины это замораживает весь процесс — все остальные запросы
воркера — на каждую паузу. Этот стор внутри корутины ждёт через `Sleeper` фичи, который
приостанавливает только вызывающего. Вне корутины остаётся `Sleep` фреймворка, так что
`Sleep::fake()` в тестах по-прежнему работает. Эта пауза —
`SConcur\Laravel\Support\CooperativeSleep`, и лимитеры фасада используют её же.

Так, например, берёт свой ключ канал управления пулом задач — через `block()`.

## Очередь

Штатный драйвер очереди `redis` из Laravel работает на этом клиенте без изменений:
`RedisQueue` обходится Lua-скриптами, `BLPOP` и несколькими обычными командами, и все они
идут через фасад.

```php
// config/queue.php
'redis' => [
    'driver'      => 'redis',
    'connection'  => 'default',   // запись из database.redis
    'queue'       => 'default',
    'retry_after' => 90,
    'block_for'   => 5,
],
```

```dotenv
REDIS_CLIENT=sconcur
QUEUE_CONNECTION=redis
```

Обычные, отложенные и пакетные задачи, повторы и `block_for` покрыты
`tests/Feature/Redis/QueueTest.php`, ключи очереди под префиксом —
`tests/Feature/Redis/PrefixTest.php`.

- Клиент выбирается в `database.redis.client` на всё приложение, поэтому очередь и `Redis::`
  работают на одном клиенте.
- `queue:work` по-прежнему выполняет по одной задаче за раз на процесс: обращения к Redis
  процесс не блокируют, но цикл воркера фреймворка последовательный.
- `bulk()` не атомарный. Фреймворк передаёт задачи в `pipeline()` и `transaction()`, но его
  колбэк отправляет их через соединение, а не через полученный пакет, поэтому задачи уходят
  по одной команде.

## Переход с phpredis

Клиент написан так, чтобы приложение на phpredis переходило на него с тем же Redis, теми же
ключами и без переноса данных: кэш остаётся прогретым, поставленные задачи остаются в
очереди, а лок, взятый до переключения, по-прежнему удерживается. Во время поэтапного деплоя
процессы, ещё работающие на phpredis, и процессы уже на `sconcur` работают с одними данными
бок о бок. Не переносится одно — значения, закэшированные с тегами: два стора хранят теги
по-разному (см. [кэш-стор](#кэш-стор)), поэтому такие значения после переключения
вычисляются заново, а тег, сброшенный процессом на одном сторе, до другого не доходит.

1. Переключите клиент и кэш-стор в `.env`:

   ```dotenv
   REDIS_CLIENT=sconcur
   CACHE_STORE=sconcur_redis
   ```

   `QUEUE_CONNECTION=redis` остаётся как есть.

2. Выпишите секцию `redis` в `config/database.php` целиком: возьмите секцию фреймворка и
   уберите то, от чего клиент отказывается. Для скелета Laravel это `max_retries` и
   `backoff_*` — упавшее соединение расширение восстанавливает само.

   ```php
   'redis' => [
       'client' => env('REDIS_CLIENT', 'sconcur'),

       'options' => [
           'cluster' => env('REDIS_CLUSTER', 'redis'),
           'prefix'  => env('REDIS_PREFIX', Str::slug((string) env('APP_NAME', 'laravel'), '_') . '_database_'),
       ],

       'default' => [
           'url'      => env('REDIS_URL'),
           'host'     => env('REDIS_HOST', '127.0.0.1'),
           'username' => env('REDIS_USERNAME'),
           'password' => env('REDIS_PASSWORD'),
           'port'     => env('REDIS_PORT', '6379'),
           'database' => env('REDIS_DB', '0'),
       ],

       'cache' => [
           'url'      => env('REDIS_URL'),
           'host'     => env('REDIS_HOST', '127.0.0.1'),
           'username' => env('REDIS_USERNAME'),
           'password' => env('REDIS_PASSWORD'),
           'port'     => env('REDIS_PORT', '6379'),
           'database' => env('REDIS_CACHE_DB', '1'),
       ],
   ],
   ```

   `prefix` оставьте ровно таким, каким он был: именно он держит ключи там, куда их положил
   phpredis. Если приложение задавало `serializer` или `compression`, здесь остановитесь —
   клиент отказывается от обоих, а значения, записанные phpredis с ними, прочитать не получится.

3. Добавьте стор в `config/cache.php` на тех же соединениях, что были у стора `redis`:

   ```php
   'sconcur_redis' => [
       'driver'          => 'sconcur_redis',
       'connection'      => env('REDIS_CACHE_CONNECTION', 'cache'),
       'lock_connection' => env('REDIS_CACHE_LOCK_CONNECTION', 'default'),
   ],
   ```

   Штатный стор `redis` не может оставаться стором кэша: его `putMany()` вызывает `multi()`.
   С теми же соединениями и тем же `cache.prefix` новый стор читает то, что записал старый, —
   см. [кэш-стор](#кэш-стор).

   Саму запись `redis` оставьте, если `SESSION_DRIVER=redis`: обработчик сессий строится на
   этом сторе по имени. Вызовы сессии до `putMany()` не доходят, но драйвер сессий `redis` на
   этом клиенте этот пакет не тестирует.

4. Проверьте собственный Redis-код приложения на осознанные отличия:
   - отвергнутая команда бросает `RedisCommandException`, а не отвечает `false`;
   - `scan()` отвечает `[курсор, элементы]`, а не двигает курсор, переданный по ссылке, и
     в его шаблон `MATCH` префикс нужно вписать самому;
   - статус, который вернул Lua-скрипт, — `'OK'`, а не `true`;
   - `Redis::connection()->client()` — объект фичи, а не `\Redis`, и префикс он никуда не
     ставит;
   - `multi()`/`exec()` отдельными вызовами превращаются в
     `Redis::transaction(function ($transaction) { ... })`, а у `watch()` замены нет.

5. Проверьте пакеты, которые работают с Redis напрямую. Пакет, требующий `ext-redis` в своём
   `composer.json`, оставляет расширение; Horizon на этом клиенте не проверялся.

6. Задеплойте и убедитесь, что данные на месте:

   ```bash
   php artisan tinker --execute="dump(Redis::keys('*'))"   # имена, которые писал phpredis, с префиксом
   php artisan tinker --execute="dump(Cache::get('some-key'))"
   php artisan queue:work --once                            # задача, поставленная до переключения, выполняется
   ```

   Когда ни один процесс больше не работает на phpredis, `ext-redis` можно удалить.

## Ограничения

- Нет кластера, sentinel и шардированного pub/sub.
- Нет `WATCH` и нет `MULTI`/`EXEC` отдельными вызовами — только `transaction()` с колбэком.
- Только RESP2.
- Штатный кэш-стор `redis` фреймворка на этом клиенте не работает: его `putMany()` вызывает
  `multi()`, а это отвергается. Используйте `sconcur_redis`.
- Драйвер сессий `redis` из Laravel этот пакет на этом клиенте не тестирует.
