# HTTP-ответы

Как воркер группы `http` превращает ответ Laravel в то, что отправляет HTTP-сервер
расширения. Каждый запрос выполняется в своей корутине; `LaravelHttpHandler`
(`src/Http/LaravelHttpHandler.php`) передаёт его ядру Laravel и возвращает серверу PSR-7
ответ. Что сервер делает с этим ответом, описано в документации библиотеки:
`vendor/sconcur/sconcur/docs/http-server.ru.md`.

## Обычные ответы

Ответ целиком преобразуется `PsrHttpFactory` из Symfony, и после этого ядро завершается
(`Kernel::terminate()`). Размер ответа известен, и сервер отправляет его одной записью с
`Content-Length`. `BinaryFileResponse` идёт тем же путём.

## Потоковые ответы

Ответ из кусков — генератор, `yield` — стримится: сначала уходят статус, заголовки и cookie,
без `Content-Length`, и сервер отправляет тело chunked-ом, пока генератор ещё работает. Тело
нигде не хранится: кусок уходит из памяти, как только сервер его отправил, а следующий
сервер берёт только после того, как клиент принял предыдущий.

### Что стримится

Любая из этих форм (`src/Http/StreamedChunks.php`):

- `new StreamedResponse($iterable)` из Symfony, в том числе наследник — iterable может быть
  генератором, массивом или любым `Traversable`;
- `response()->stream(function () { yield …; })` из Laravel;
- `StreamedResponse`, колбэк которого сам является функцией-генератором
  (`->setCallback(fn () => yield …)`).

```php
return new StreamedResponse((static function () use ($cursor): Generator {
    yield '{"items":[';

    foreach ($cursor as $index => $item) {
        yield ($index > 0 ? ',' : '') . json_encode($item);
    }

    yield ']}';
})(), 200, ['Content-Type' => 'application/json']);
```

Первые две формы без изменений работают и вне этого сервера: под PHP-FPM Symfony и Laravel
печатают каждый кусок и сбрасывают его. Третья — форма Octane: под PHP-FPM генератор колбэка
никто не перебирает, и тело пустое.

Чтобы распознать первые две формы, мост читает переменные замыкания, в которое
Symfony и Laravel заворачивают куски. Нераспознанная форма — не ошибка: такой ответ
отправляется целиком, как колбэк, который печатает.

### Как читаются куски

Каждый отданный кусок — отдельный кусок на проводе, было между ними ожидание или нет, так
что стримит и генератор, который только вычисляет (`src/Http/IterableResponseBody.php`).

Генератор выполняется на стеке того, кто его продвигает, — здесь это корутина запроса.
Поэтому он работает как любой код обработчика:

- `request()`, `auth()`, сессия и остальные сервисы корутины — те же, что видел контроллер;
- то, чего он ждёт (пачка курсора, запрос, `Sleeper`, `WaitGroup`), приостанавливает
  корутину запроса обычным образом и даёт поработать остальным запросам воркера;
- вытеснение и `handlerTimeoutMs` достают его, как любой обработчик.

Кусок — строка; целое, дробное, `null` или `Stringable` превращаются в строку так же, как это
сделал бы `echo`. Всё остальное обрывает тело с `UnexpectedValueException`.

### Завершение запроса

`Kernel::terminate()` — terminable middleware и колбэки `terminating` — выполняется после
последнего куска, а не до первого. Если тело не дочитано (клиент ушёл, обработчик вышел за
`handlerTimeoutMs`), ядро завершается, когда сервер отпускает ответ. В останавливающемся
воркере ядро не завершается.

Генератор освобождается вместе с ответом, поэтому блоки `finally` недочитанного генератора
могут выполниться после завершения.

### Ошибки

Статус и заголовки уходят до того, как взят первый кусок, поэтому статус уже не поменять.
Исключение из генератора обрывает тело: оно передаётся обработчику исключений Laravel
(`report()`), поток закрывается чисто, а ядро всё равно завершается. Клиент видит оборванное
тело, а не страницу ошибки. Остановка — `handlerTimeoutMs`, выключение воркера — не
репортится.

`handlerTimeoutMs` покрывает весь запрос вместе со стримингом.

### Колбэк, который печатает

`StreamedResponse`, колбэк которого печатает через `echo`, не стримится: он отправляется
целиком, как обычный ответ. `PsrHttpFactory` выполняет колбэк до конца в `php://temp`
(первые 2 МБ в памяти, остальное на диске), и клиент получает первый байт, когда колбэк
закончил. Это касается `StreamedJsonResponse`, `response()->streamJson()`,
`response()->streamDownload()`, `response()->eventStream()` и любого колбэка с `echo`.

Чтобы такой ответ стримился, его нужно написать через `yield`:

```php
// отправляется целиком
return new StreamedResponse(static function () use ($rows): void {
    foreach ($rows as $row) {
        echo implode(',', $row) . "\n";
    }
});

// стримится
return new StreamedResponse((static function () use ($rows): Generator {
    foreach ($rows as $row) {
        yield implode(',', $row) . "\n";
    }
})());
```

Колбэк, который печатает, выполняется под буфером вывода, поэтому к нему относится всё, что
сказано в разделе [Буферы вывода](#буферы-вывода).

## Буферы вывода

Буферы вывода PHP (`ob_start()`, `ob_get_clean()`) принадлежат процессу, а не корутине.
Корутина, приостановленная с открытым буфером, оставляет его на стеке для остальных: сосед
открывает свой поверх, и каждый следующий `ob_get_clean()` снимает верхний буфер — не
обязательно свой. Вывод двух запросов смешивается.

Корутина приостанавливается с открытым буфером в двух случаях:

- она ждёт фичу внутри буфера — запрос, пока рендерится шаблон (ленивая загрузка связи),
  команда Redis, `Sleeper`;
- её паркует вытеснение: HTTP-сервер прерывает обработчик каждые `preemptionQuantumMs`
  процессорного времени (по умолчанию 5 мс), так что достаточно рендера дольше кванта.

Так рендерит Blade и любой шаблонизатор на PHP: `ob_start()`, шаблон, `ob_get_clean()`. Так
же выполняется и `StreamedResponse`, который печатает. Шаблоны, которые не загружают данных
и укладываются в квант, не затронуты; шаблоны, которые ждут внутри или рендерятся дольше,
затронуты, как только два таких запроса выполняются в одном воркере.

Что уводит ответ из-под этого:

- загружать данные до рендера, чтобы внутри шаблона ничего не ждало;
- стримить через `yield`, а не через `echo`, — генератор буфер не использует вовсе;
- `preemptionQuantumMs = 0` в блоке `server` группы `http` выключает вытеснение. Это убирает
  второй случай, но не первый, и позволяет обработчику, занятому вычислениями, держать
  остальные запросы своего воркера.
